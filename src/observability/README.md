# src/observability

Structured logging, metrics, and distributed tracing — Phase 8 (observability and production hardening). Builds on the health-check and error-filter scaffolding that already existed (see `src/modules/health/README.md` and `src/common/filters/README.md`, both of which called out this work as a forward reference before it existed).

## Subfolders

| Folder | Purpose |
|---|---|
| `logging` | Correlation-id propagation for structured logs. JSON log formatting itself uses Nest's own built-in `ConsoleLogger` `json: true` option (wired in `src/main.ts`), not a custom logger class — no new logging dependency was needed. |
| `metrics` | Prometheus metrics (`@willsoto/nestjs-prometheus` + `prom-client`) — HTTP request counters/latency and BullMQ queue depth, exposed at `GET /v1/metrics`. |
| `tracing` | OpenTelemetry SDK bootstrap, exported via OTLP to a local Jaeger container (see `docker-compose.yml`). |

## Files

| File | Purpose | Why |
|---|---|---|
| `logging/correlation-id.middleware.ts` (`CorrelationIdMiddleware`) | Assigns a correlation id to every request — reused from an incoming `x-correlation-id` header when present, otherwise generated fresh via `randomUUID()`. Attached to `request.correlationId` (see `src/common/auth/request-context.ts`) and echoed back on the response. Applied globally via `app.use(...)` in `main.ts` rather than `NestModule.configure()`, since it needs to run for every route with no per-module opt-in. | Lets a single request be traced across logs even without full distributed tracing, and lets a caller correlate their own logs with ours by reusing the same header on a retried/downstream request. |
| `metrics/metrics.providers.ts` | Defines the three custom Prometheus metrics as `@willsoto/nestjs-prometheus` providers: `http_requests_total` (counter), `http_request_duration_seconds` (histogram), `queue_depth` (gauge). | Centralizes metric names/label definitions in one place so the interceptor, the queue poller, and any future consumer all reference the same string constants instead of re-typing metric names. |
| `metrics/http-metrics.interceptor.ts` (`HttpMetricsInterceptor`) | Global interceptor (applied via `app.useGlobalInterceptors` in `main.ts`) recording one counter increment + one histogram observation per HTTP request, labeled by method/route/status code. | Reads the route label from `request.route.path` (the matched Express pattern, e.g. `/v1/projects/:id/events`) rather than `request.url`, so requests to the same endpoint with different path params collapse into one label combination instead of creating unbounded cardinality — a real concern with per-request metrics. |
| `metrics/queue-metrics.service.ts` (`QueueMetricsService`) | Polls `getWaitingCount()`/`getActiveCount()` on both BullMQ queues (`SNAPSHOT_CREATION_QUEUE`, `REPLAY_JOBS_QUEUE` from `src/queues/queue-names.ts`) on an interval (default 10s, overridable via `QUEUE_METRICS_POLL_INTERVAL_MS`) and sets the `queue_depth` gauge accordingly. The first poll happens after one full interval, not immediately on boot. | BullMQ has no push-based depth event, so polling is the only option; the gauge simply reflects whatever the last poll observed between scrapes, which is acceptable since queue depth changes on the order of seconds, not milliseconds. The poll interval's `setInterval` handle is `.unref()`'d so it never keeps the process alive on its own. Made configurable (and slowed to an hour in tests via `test/jest.setup.ts`) as a precaution against every e2e spec file's own `AppModule` instance running this poller concurrently — this turned out **not** to be the cause of a separate flaky replay-job test (see `test/README.md`'s "Known issue" section for the actual root cause, which is unrelated stale BullMQ worker connections across test files), but the configurability is harmless to keep regardless. |
| `metrics/metrics.module.ts` (`MetricsModule`) | Registers `PrometheusModule.register({ path: '/metrics', defaultMetrics: { enabled: true } })`, the three metric providers, `QueueMetricsService`, and `HttpMetricsInterceptor`; exports `HttpMetricsInterceptor` so `main.ts` can resolve it via `app.get(...)` for the global interceptor registration. | Imported once in `app.module.ts`. `defaultMetrics: { enabled: true }` additionally exposes standard Node.js process metrics (CPU, memory, event loop lag) for free. |
| `tracing/tracing.ts` | Standalone OpenTelemetry `NodeSDK` bootstrap — **not** imported by any other module. Configures `getNodeAutoInstrumentations()` (patches `http`, `express`, `pg`, `ioredis`, and others) and an `OTLPTraceExporter` pointed at `OTEL_EXPORTER_OTLP_TRACES_ENDPOINT` (defaults to the local Jaeger container's `http://localhost:4318/v1/traces`). Set `OTEL_DEBUG=1` to enable OpenTelemetry's own verbose diagnostic logging when debugging instrumentation issues. | See "Why tracing is a separate preloaded file" below — this **cannot** be a normal Nest module or a static import in `main.ts`. |

## Why tracing is a separate preloaded file (confirmed with the user)

OpenTelemetry's Node auto-instrumentation works by monkey-patching a library's exports the moment that library is first `require`'d (e.g. wrapping `pg.Client.prototype.query`). This means the SDK must call `.start()` **before** anything else in the process requires `pg`, `ioredis`, `http`, etc. `main.ts` statically imports `AppModule` at the very top of the file, and since Node evaluates static imports before a file's own function bodies run, any instrumentation code placed inside `bootstrap()` would always run too late — every DB/Redis/HTTP client would already be loaded and un-patchable by the time it executed.

The fix is to load `tracing.ts` as a `node -r` (`--require`) preload, entirely separate from and before `main.ts`'s own module graph: `node -r ./tracing.js -r ts-node/register ... main.ts` (see `package.json`'s `start`/`start:dev`/`start:debug`/`start:prod` scripts). This is the standard, OpenTelemetry-docs-recommended pattern for Node auto-instrumentation, not a project-specific workaround.

### A structural consequence: `nest start`/`nest start --watch` had to be replaced in dev scripts

`@nestjs/cli`'s `nest start` command spawns the actual app in a **separate child process** (see `node_modules/@nestjs/cli/lib/runners/abstract.runner.js`'s use of `child_process.spawn`). A `-r` preload on the outer `node` process invoking `nest start` never reaches that child process, so tracing silently never activated in dev mode even though `start:prod`'s plain `node dist/main` worked fine (confirmed by testing: `/v1/health` requests never appeared in Jaeger's service list under the old `nest start --watch`-based scripts, despite instrumentation loading and reporting no errors). `start`/`start:dev`/`start:debug` now bypass the Nest CLI runner and invoke `ts-node` directly (via `nodemon` for the watch/reload behavior in the `:dev`/`:debug` variants), so the same `-r` preload chain that works for `start:prod` also works in dev — verified end-to-end via a real trace appearing in Jaeger with request → `HealthController.getReadiness` → `pg.connect`/`pg.query` → `ioredis` `ping` spans.

### `scripts/resolve-ts-js-specifiers.js`

A second, small `-r` preload (loaded **before** `ts-node/register`) that exists purely to work around a real incompatibility: `prisma/schema.prisma`'s generated client (`src/generated/prisma/`) is written `nodenext`-style, using explicit `.js` specifiers in its own internal imports (e.g. `import ... from './internal/class.js'`) even though only the sibling `.ts` source exists on disk. `nest build`'s `tsc` compile resolves this fine (it emits real `.js` files), and Jest's config already works around it via `moduleNameMapper: { "^(\\.{1,2}/.*)\\.js$": "$1" }` (see both Jest configs) — but plain `ts-node/register` has no built-in equivalent, so running `main.ts` directly through it (a prerequisite for fixing the tracing preload issue above) crashed with `Cannot find module './internal/class.js'` the moment `PrismaService` was imported. The hook patches `Module._resolveFilename` to retry a failed `.js`-suffixed relative specifier without the extension, mirroring what Jest's `moduleNameMapper` already does, so `ts-node`'s CJS resolution can fall through to the `.ts` source.

## Design decisions (confirmed with the user)

- **Logging**: Nest's built-in `ConsoleLogger` JSON mode, not a third-party logging library (e.g. Pino) — avoids a new dependency for a need the framework already covers natively in this Nest version.
- **Metrics**: Prometheus + OpenTelemetry tracing, the more thorough of the offered options, over a metrics-only or logging-only scope for this phase.
- **Tracing export target**: a local Jaeger container via OTLP (added to `docker-compose.yml`), giving a real UI to inspect traces, over a bare console exporter.
- **Error response format**: left as-is (`src/common/filters/all-exceptions.filter.ts`'s existing `{ statusCode, message, timestamp, path }` shape) — audited for consistency rather than extended with a new machine-readable error-code field.
