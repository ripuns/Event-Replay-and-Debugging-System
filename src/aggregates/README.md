# src/aggregates

Aggregate state reconstruction — the second (and final) piece of Phase 5, after `src/events`' append API. Given a project + aggregate, replays that aggregate's events in sequence order and folds them into a single state object using the project's declared `event_reducers` rules (see `src/event-reducers/README.md`).

## Files

| File | Purpose | Why |
|---|---|---|
| `aggregates.controller.ts` (`AggregatesController`) | `GET /v1/projects/:id/aggregates/:aggregateId/state` — optional `?asOfSequence=N` query param for point-in-time ("time-travel") reconstruction; defaults to the latest event when omitted. Guarded by `ApiKeyGuard` + `ProjectAccessGuard` (which reads `request.params.id`, unaffected by the extra `aggregateId` param on this route). Validates `asOfSequence` is a positive integer string before it reaches the service, returning `400` otherwise. | `asOfSequence` support is not incidental — it's the direct realization of ReplayDB's stated purpose ("time-travel debugging") from `CONTEXT_SUMMARY.md` §1-2; a "latest state only" endpoint wouldn't actually deliver what the project is for. |
| `aggregates.service.ts` (`AggregatesService`) | `getState(projectId, aggregateId, asOfSequence?)`: loads the aggregate (404 if it doesn't belong to `projectId` — enforces project isolation the same way every other project-scoped lookup does), loads its events up to `asOfSequence` in sequence order, loads the project's reducer rules for that aggregate's `aggregateType`, folds them via `reduceEvents`, and returns `{ aggregateId, aggregateType, aggregateKey, asOfSequence, state }` (`asOfSequence` in the response reflects the actual last-applied event's sequence number, `null` if the aggregate has no events yet). | Rules coming back from Prisma are typed `operation: string` (the DB column), but `reduceEvents` expects the `EventReducerOperation` enum — the service filters out any row whose `operation` isn't one of the three known values before mapping, as a defensive boundary check (the DB `CHECK` constraint already guarantees this in practice, but the TypeScript type system doesn't know that, and a stricter check here costs nothing). |
| `aggregates.repository.ts` (`AggregatesRepository`) | `findForProject(aggregateId, projectId)` — the project-scoped existence check. `findEventsUpTo(aggregateId, asOfSequence?)` — all events for that aggregate ordered by `sequenceNumber` ascending, optionally capped with `sequenceNumber <= asOfSequence`. | Plain Prisma wrapper, same layering as every other repository in this codebase. |
| `reduce-events.ts` (`reduceEvents`, `ReducibleEvent`, `ReducerRule`) | The actual fold: for each event in order, look up its `eventType`'s rule (`Map` keyed by event type) and apply it — `set` shallow-merges payload into the state root, `merge` shallow-merges payload into `state[field]`, `append` pushes payload onto the array at `state[field]`. An event with no matching rule is skipped, not an error — reconstruction stays total (never crashes) even against event types nobody has registered a rule for yet. | Deliberately a pure, dependency-free function (no Prisma, no Nest) so the reduction logic itself is trivially unit-testable in isolation from HTTP/DB concerns — see `reduce-events.spec.ts`. |
| `reduce-events.spec.ts` | Unit tests for `reduceEvents` covering all three operations, ordering (later events overwriting earlier `set` fields), the skip-unmapped-event-type behavior, and a `merge`/`append` rule missing its `field`. | Fast, no-DB coverage of the core folding logic — the e2e suite (`test/aggregates.e2e-spec.ts`) covers the same behavior end-to-end through real HTTP/DB, but these unit tests pin down edge cases (e.g. missing `field`) more cheaply. |
| `aggregates.module.ts` (`AggregatesModule`) | Imports `PrismaModule`, `ApiKeyModule`, `EventReducersModule`; provides the service/repository/guards; registers the controller; exports `AggregatesService`. | Imports `EventReducersModule` (rather than duplicating a reducer-lookup provider) since reconstruction needs the project's declared rules — one-way dependency, no cycle. |

## Not built yet (deliberately out of scope for this slice)

- Snapshot creation/lookup as a performance optimization for reconstruction (replaying from scratch every time) — that's `snapshots`, explicitly Phase 6 per `CONTEXT_SUMMARY.md`.
- `increment`/`remove` reducer operations — see `src/event-reducers/README.md`.
