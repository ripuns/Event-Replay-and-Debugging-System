# src/aggregates

Aggregate state reconstruction — built in Phase 5 (event replay + reducer-based folding), accelerated in Phase 6 (snapshot-aware replay), and cached in Phase 7 (Redis, see `src/cache/README.md`). Given a project + aggregate, replays that aggregate's events in sequence order and folds them into a single state object using the project's declared `event_reducers` rules (see `src/event-reducers/README.md`), starting from the nearest snapshot when one exists (see `src/snapshots/README.md`) instead of always replaying from the first event, and checking Redis before touching Postgres at all.

## Files

| File | Purpose | Why |
|---|---|---|
| `aggregates.controller.ts` (`AggregatesController`) | `GET /v1/projects/:id/aggregates/:aggregateId/state` — optional `?asOfSequence=N` query param for point-in-time ("time-travel") reconstruction; defaults to the latest event when omitted. Guarded by `ApiKeyGuard` + `ProjectAccessGuard` (which reads `request.params.id`, unaffected by the extra `aggregateId` param on this route). Validates `asOfSequence` is a positive integer string before it reaches the service, returning `400` otherwise. | `asOfSequence` support is not incidental — it's the direct realization of ReplayDB's stated purpose ("time-travel debugging") from `CONTEXT_SUMMARY.md` §1-2; a "latest state only" endpoint wouldn't actually deliver what the project is for. |
| `aggregates.service.ts` (`AggregatesService`) | `getState(projectId, aggregateId, asOfSequence?)`: first checks the Redis state cache (`aggregate-state:{id}:latest` or `:seq:{N}`, via `RedisCacheService`) — a hit returns immediately, skipping Postgres entirely. On a miss: loads the aggregate (404 if it doesn't belong to `projectId`), calls the private `getSnapshotLookup` helper (which itself checks a separate `snapshot-lookup:{id}:...` cache before falling through to `SnapshotsRepository.findLatestUpTo`), loads only the events *after* the snapshot's sequence number (`findEventsInRange`) up to `asOfSequence`, loads the project's reducer rules, and folds the events starting from the snapshot's `state` instead of `{}`. The final result is written into the state cache (300s TTL) before returning. Correctness never depends on either cache layer or a snapshot existing — with all three absent, this degrades to exactly the Phase-5 behavior (replay every event from the start); a query for a point *before* any available snapshot correctly ignores that snapshot and replays from scratch (verified in `test/snapshots-and-replay-jobs.e2e-spec.ts` and `test/cache.e2e-spec.ts`). | Rules coming back from Prisma are typed `operation: string` (the DB column), but `reduceEvents` expects the `EventReducerOperation` enum — the service filters out any row whose `operation` isn't one of the three known values before mapping, as a defensive boundary check. Two cache layers (full state, snapshot lookup) rather than one exist because a state-cache miss still benefits from a cached snapshot lookup — see `src/cache/README.md` for why layering them doesn't increase staleness risk (both invalidate together at the same trigger points). |
| `aggregates.repository.ts` (`AggregatesRepository`) | `findForProject(aggregateId, projectId)` — the project-scoped existence check. `findEventsInRange(aggregateId, afterSequence?, upToSequence?)` — events for that aggregate strictly after `afterSequence` (the snapshot's sequence number, if any) and at or before `upToSequence`, ordered ascending. | Renamed from `findEventsUpTo` (Phase 5) to `findEventsInRange` (Phase 6) once a lower bound was needed for snapshot-aware replay — same plain-Prisma-wrapper layering as every other repository in this codebase. |
| `reduce-events.ts` (`reduceEvents`, `ReducibleEvent`, `ReducerRule`) | The actual fold: for each event in order, look up its `eventType`'s rule (`Map` keyed by event type) and apply it — `set` shallow-merges payload into the state root, `merge` shallow-merges payload into `state[field]`, `append` pushes payload onto the array at `state[field]`. An event with no matching rule is skipped, not an error. Takes an optional third `initialState` parameter (default `{}`) so a caller can resume folding from a snapshot's `state` instead of always starting empty — the `events` array passed in is then expected to contain only events after that snapshot's sequence number. | Deliberately a pure, dependency-free function (no Prisma, no Nest, no cache) so the reduction logic itself is trivially unit-testable in isolation — see `reduce-events.spec.ts`. |
| `reduce-events.spec.ts` | Unit tests for `reduceEvents` covering all three operations, ordering, the skip-unmapped-event-type behavior, and a `merge`/`append` rule missing its `field`. | Fast, no-DB coverage of the core folding logic — the e2e suites cover the same behavior end-to-end through real HTTP/DB. |
| `aggregates.module.ts` (`AggregatesModule`) | Imports `PrismaModule`, `ApiKeyModule`, `EventReducersModule`, `CacheModule` (Phase 7); provides the service/repository/guards **and `SnapshotsRepository`** (Phase 6); registers the controller; exports `AggregatesService`. | `SnapshotsRepository` (not the whole `SnapshotsModule`) is provided directly here to avoid a module import cycle: `SnapshotsModule` imports `AggregatesModule` for `AggregatesService` (snapshot creation calls back into reconstruction), so `AggregatesModule` cannot import `SnapshotsModule` in return. `SnapshotsRepository` is a stateless Prisma wrapper with no dependency on `AggregatesService`, so providing it in both modules is harmless — same pattern used for `ProjectsRepository` earlier in this codebase. `CacheModule` has no such conflict and is imported normally. |

## A real bug found via testing, not review

An early version of the Phase-6-era test `test/snapshots-and-replay-jobs.e2e-spec.ts` asserted the automatic snapshot lands at *exactly* sequence 20 (the threshold). Adding caching in Phase 7 changed timing enough to expose that this assumption was never actually guaranteed: snapshot creation runs asynchronously in a queue worker (see `src/snapshots/README.md`), so by the time it runs, more events may already have landed. The test now asserts the snapshot lands at `>= 20`, matching `SnapshotsService.createSnapshot`'s documented behavior, rather than the exact triggering sequence number.
