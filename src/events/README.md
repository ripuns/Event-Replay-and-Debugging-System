# src/events

Event append API — the first write path into the actual event store (Phase 5). Events are immutable and append-only; there is no update/delete endpoint by design (see `CONTEXT_SUMMARY.md` §8, "keep event history immutable").

## Files

| File | Purpose | Why |
|---|---|---|
| `events.controller.ts` (`EventsController`) | `POST /v1/projects/:id/events` — guarded by `ApiKeyGuard` + `ProjectAccessGuard` (same `:id` param convention as `ProjectsController`). Delegates straight to `EventsService.append`. Annotated with `@ApiTags('events')`/`@ApiBearerAuth('api-key')`/`@ApiOperation` for Swagger. | Thin controller — all aggregate-resolution and sequencing logic lives in the service/repository layer. |
| `events.service.ts` (`EventsService`) | `append(projectId, input)`: runs the whole append (find-or-create aggregate, compute next sequence number, insert event) inside one `prisma.$transaction`. Converts the returned `sequenceNumber` (a Prisma `BigInt`) to a `string` before returning, since `JSON.stringify`/Express's `res.json()` cannot serialize `BigInt` natively — this was a real bug caught during manual testing (`TypeError: Do not know how to serialize a BigInt`), not a preemptive guess. | The transaction boundary is what makes "auto-create the aggregate on first event" and "assign the next sequence number" atomic with the actual event insert — without it, a concurrent request could interleave between steps and produce duplicate or gapped sequence numbers. |
| `events.repository.ts` (`EventsRepository`) | `findOrCreateAggregateForUpdate(tx, ...)`: raw `INSERT ... ON CONFLICT (project_id, aggregate_type, aggregate_key) DO NOTHING`, followed by `SELECT ... FOR UPDATE` to fetch and row-lock the (now guaranteed-to-exist) aggregate. `nextSequenceNumber(tx, aggregateId)`: `MAX(sequence_number)+1` for that aggregate, computed inside the same transaction/lock. `createEvent(tx, data)`: plain `event.create`. `findById(eventId)`. | The raw `INSERT ... ON CONFLICT DO NOTHING` (rather than Prisma's `upsert()`) exists because of a real concurrency bug found under load testing: `upsert()`'s create/update are two separate statements, so under `READ COMMITTED` isolation two concurrent requests appending to the *same new* aggregate could both see "no row exists," both attempt the create, and the loser would crash on the unique constraint instead of falling back to update. `ON CONFLICT DO NOTHING` resolves the race atomically in Postgres itself. Verified by firing 15-20 concurrent appends to a brand-new aggregate and confirming gapless, unique sequence numbers every time (see `test/events.e2e-spec.ts`). |
| `events.module.ts` (`EventsModule`) | Imports `PrismaModule`, `ApiKeyModule`; provides `EventsService`/`EventsRepository`/`ApiKeyGuard`/`ProjectAccessGuard`; registers `EventsController`; exports `EventsService`. | Same layering as `organization`/`projects`/`api-keys` modules. Registered directly in `app.module.ts` (not nested inside `ProjectsModule`) since its route family (`/v1/.../events`) is its own top-level concern per the API design in `CONTEXT_SUMMARY.md` §18. |
| `dto/append-event.dto.ts` (`AppendEventDto`) | `class-validator`/`@ApiProperty` DTO: `aggregateType` (string, max 100 — matches the DB column width), `aggregateKey` (string, max 255), `eventType` (string, max 255), `eventVersion` (int ≥ 1), `payload` (required object), `metadata` (optional object), `occurredAt` (optional ISO date string, defaults to "now" in the service if omitted). | Validated by the global `ValidationPipe` before reaching the controller. `occurredAt` has no ordering check against previous events for the same aggregate — `sequence_number`, not `occurredAt`, is the authoritative order (a deliberate decision: late-arriving events from an upstream queue are legitimate). |

## Design decisions (confirmed with the user)

- **Aggregates auto-create on first event** — no separate "register an aggregate" endpoint. `aggregateType`+`aggregateKey` act as the natural key; the first event for a new pair creates the aggregate row as a side effect.
- **Sequence numbers are server-assigned**, not client-supplied — computed as `MAX(sequence_number)+1` per aggregate, inside the same transaction that locks the aggregate row, so it's safe under concurrency (see the repository entry above).
- **One event per request** for this first pass — no batch-append endpoint yet. Revisit only if a real throughput need shows up; batching correctly (atomic sequence assignment across a whole array) is meaningfully more complex than the single-event path.
