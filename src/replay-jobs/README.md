# src/replay-jobs

Bulk, async aggregate reconstruction — the second half of Phase 6. A replay job recomputes state (and writes fresh snapshots) for every aggregate matching a project-wide or `aggregateType`-scoped selection, tracked as a `ReplayJob` row the caller can poll. This is distinct from `GET /v1/projects/:id/aggregates/:aggregateId/state` (Phase 5, single aggregate, synchronous) — a replay job targets *many* aggregates and runs *asynchronously*, since replaying thousands of aggregates in one HTTP request isn't viable.

## Files

| File | Purpose | Why |
|---|---|---|
| `replay-jobs.controller.ts` (`ReplayJobsController`) | `POST /v1/projects/:id/replay-jobs` — creates a job (optionally scoped to `{ aggregateType }`; omit for the whole project) and enqueues it, returning immediately with `status: pending`. `GET /v1/projects/:id/replay-jobs/:jobId` — poll for status/result. Both guarded by `ApiKeyGuard` + `ProjectAccessGuard`. | The create endpoint deliberately does not wait for the job to finish — that's the entire point of making this async rather than reusing the synchronous `aggregates/:id/state` endpoint. |
| `replay-jobs.service.ts` (`ReplayJobsService`) | `create(projectId, aggregateType?)` — persists a `pending` `ReplayJob` row, enqueues `{ jobId }` on `REPLAY_JOBS_QUEUE`, returns the row. `findOne(jobId, projectId)` — project-scoped lookup, 404 if not found or not in this project. | Thin service; all the actual bulk-processing logic lives in the processor, not here — this layer only owns job lifecycle bookkeeping. |
| `replay-jobs.repository.ts` (`ReplayJobsRepository`) | `create`, `findForProject`, `markRunning`, `markCompleted(jobId, result)`, `markFailed(jobId, error)`, `findAggregateIdsForScope(projectId, aggregateType?)`. | `error` is truncated to 255 chars before writing (`error.slice(0, 255)`) to match the `replay_jobs.error VARCHAR(255)` column — an unbounded error message would otherwise throw a second, more confusing error while trying to record the first one. |
| `replay-job.processor.ts` (`ReplayJobProcessor`) | BullMQ `@Processor(REPLAY_JOBS_QUEUE)` — marks the job `running`, finds every aggregate in scope (`findAggregateIdsForScope`), calls `SnapshotsService.createSnapshot` for each one, and marks the job `completed` with a `result` summary (`{ aggregatesProcessed, snapshotsCreated, failures: [{aggregateId, error}] }`) or `failed` if something outside the per-aggregate loop throws. A per-aggregate failure is caught and recorded in `failures`, not allowed to abort the whole job — one bad aggregate shouldn't prevent every other aggregate in scope from being processed. | Reuses `SnapshotsService.createSnapshot` rather than duplicating reconstruction logic — a replay job's real "output" *is* the fresh snapshots it writes; `result` is a human-readable summary of that, not a separate source of truth (see the "replay job output" design decision below). |
| `dto/create-replay-job.dto.ts` (`CreateReplayJobDto`) | `aggregateType` (optional string, max 100). | Optional by design — omitting it targets every aggregate in the project, matching the "bulk reconstruction across many aggregates" scope this feature exists for. |
| `replay-jobs.module.ts` (`ReplayJobsModule`) | Imports `PrismaModule`, `ApiKeyModule`, `SnapshotsModule`, `QueuesModule`, registers `REPLAY_JOBS_QUEUE`; provides service/repository/processor/guards; registers the controller; exports `ReplayJobsService`. | Standard layering, consistent with every other domain module. |

## Design decisions (confirmed with the user)

- **Output**: no separate per-aggregate results table — a job's real output is the snapshot rows it writes; `replay_jobs.result` (added in `V005__add_replay_job_scope_and_result.sql`) is a JSONB summary, not a second source of truth. Avoids over-engineering a feature whose real output already lives in `snapshots`.
- **Cancellation**: not supported in this first version. A job runs to completion, failure, or until the process restarts (BullMQ's default retry policy applies). No `POST .../replay-jobs/:jobId/cancel` endpoint, no cooperative-cancellation checks in the processor loop.
- **Scope**: `aggregateType` (added to `ReplayJob` alongside `result`) lets a job target "every aggregate of this type," not just one specific aggregate (the pre-existing but unused `aggregateId` column) or the literal entire project with no filter at all.
