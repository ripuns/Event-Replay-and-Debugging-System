# src/modules/health

Liveness and readiness endpoints. Liveness (`GET /v1/health`) was the first module scaffolded in the project (Phase 0), used to verify the app boots and responds before any real domain logic existed. Readiness (`GET /v1/health/ready`) was added in Phase 8 (observability/hardening).

## Files

| File | Purpose | Why |
|---|---|---|
| `health.controller.ts` (`HealthController`) | `GET /v1/health` → delegates to `HealthService.getHealth()`. `GET /v1/health/ready` → delegates to `HealthService.getReadiness()`. | Thin controller, no logic of its own — matches the project rule "keep controllers thin." |
| `health.service.ts` (`HealthService`) | `getHealth()` returns `{ status: 'ok', service: 'replaydb-api', timestamp }` — a simple synchronous check, unchanged since Phase 0. `getReadiness()` actively checks Postgres (`prisma.$queryRaw\`SELECT 1\``) and Redis (`redis.ping()`, via the raw `REDIS_CLIENT` token, **not** `RedisCacheService`) in parallel, returning `{ status: 'ready' \| 'not_ready', service, timestamp, checks: [{ name, status, error? }] }`. Throws `ServiceUnavailableException` (503) when either check fails. | `RedisCacheService` deliberately fails open on every method (returns `null`/no-op on any Redis error, see `src/cache/README.md`) so it can't distinguish "cache miss" from "Redis is down" — readiness needs to see the real failure, so it talks to the raw `ioredis` client directly instead. Liveness (`getHealth`) intentionally stays a pure in-process check with no dependency pings — a process that's up but can't reach its dependencies should report `ready: false`, not `alive: false`; killing/restarting a live-but-dependency-starved process would not help it recover. |
| `health.module.ts` (`HealthModule`) | Imports `CacheModule` (for the `REDIS_CLIENT` token). `PrismaService` is available without an explicit import since `PrismaModule` is `@Global()`. Registers `HealthController`/`HealthService`. | Standard Nest module; imported unconditionally in `app.module.ts` since health should always be reachable regardless of other modules' state. |
| `health.controller.spec.ts` | Unit tests for `HealthController` — one for `getHealth()`, one confirming `getReadiness()` delegates to `HealthService.getReadiness()` (mocked, since a unit test shouldn't need real Postgres/Redis). `PrismaService` and `REDIS_CLIENT` are provided as trivial mocks (`{ $queryRaw: jest.fn() }`, `{ ping: jest.fn() }`) purely so `HealthService` can be constructed — the real dependency-check behavior is exercised in `test/health.e2e-spec.ts`'s (or a dedicated e2e readiness test's) real-infra path, not here. | Confirms the controller returns whatever the service produces, isolated from HTTP/Nest bootstrap (see `test/health.e2e-spec.ts` for the full-stack version). |

## Why readiness is separate from liveness

A process can be alive (event loop running, able to accept connections) while still not ready to serve real traffic (e.g. Postgres/Redis unreachable). Liveness answers "should this process be restarted?" — readiness answers "should this instance receive traffic right now?" Conflating them means a transient DB blip needlessly restarts an otherwise-healthy process instead of just being routed around until the dependency recovers.
