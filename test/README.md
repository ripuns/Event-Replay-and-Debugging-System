# test

End-to-end (e2e) tests — boot the full Nest app (`AppModule`) and hit real HTTP routes via `supertest`, as opposed to the isolated unit specs colocated with their modules (e.g. `src/modules/health/health.controller.spec.ts`).

## Files

| File | Purpose | Why |
|---|---|---|
| `health.e2e-spec.ts` | Boots the app with the global `/v1` prefix and asserts `GET /v1/health` returns `{ status: 'ok', service: 'replaydb-api', timestamp }`. | Confirms the app actually starts end-to-end (config validation, module wiring, DI graph) — not just that individual units work in isolation. |
| `organization.e2e-spec.ts` | Boots the app and hits real `/v1/organizations` routes against the live Postgres from `.env`'s `DATABASE_URL`: creating an org with a bootstrapped `firstProject`+API key, creating a bare org (no `firstProject`), and confirming `GET /v1/organizations/:id` is rejected without a valid key. Cleans up every org (and cascaded projects/keys) it creates in `afterEach` via `PrismaService`. | Verifies the atomic org+project+key bootstrap transaction actually persists correctly and that the `ApiKeyGuard`/org-id check on `GET /v1/organizations/:id` works against a real database, not just in isolation. |
| `projects.e2e-spec.ts` | Boots the app and exercises `/v1/organizations/:orgId/projects`, `/v1/projects/:id`, and `/v1/projects/:id/api-keys`: creating a second project in an org with an existing key, confirming a key from one project is rejected (`403`) on another project in the same org, confirming a key from a different org is rejected (`403`) on `:orgId/projects`, confirming no key is rejected (`401`), and minting an additional key for a project. Same `afterEach` cleanup pattern as `organization.e2e-spec.ts`. | This is the actual proof of the project-isolation guarantee described in `src/common/auth/README.md` and `database/migrations/README.md` — a passing suite here means the composite-FK isolation at the DB level and the guard-level isolation at the HTTP level agree with each other. |
| `events.e2e-spec.ts` | Boots the app and exercises `POST /v1/projects/:id/events`: auto-creating an aggregate on its first event (sequence number `1`), independent/increasing sequence numbers across separate `append` calls to the same vs. different aggregates, **15 concurrent appends to a brand-new aggregate** asserted to produce unique gapless sequence numbers `1..15` with no `500`s, and rejection (`401`) without a valid key. Same `afterEach` cleanup pattern (deletes events/aggregates/keys/projects/orgs it created). | The concurrency test is not a hypothetical — it's the regression test for a real race condition found during manual load testing (`EventsRepository.findOrCreateAggregateForUpdate`'s original `Prisma.upsert()`-based implementation crashed under concurrent first-appends to a new aggregate; see `src/events/README.md` for the root cause and fix). Keeping this test running against the real Postgres, not a mock, is what actually catches this class of bug — a mocked Prisma client can't reproduce a `READ COMMITTED` race. |
| `aggregates.e2e-spec.ts` | Boots the app and exercises `GET /v1/projects/:id/aggregates/:aggregateId/state`: registering `set`/`merge`/`append` reducer rules, appending a mix of mapped and unmapped event types and confirming the final reconstructed state matches exactly (including that the unmapped event contributed nothing), point-in-time reconstruction via `?asOfSequence=N` confirming a field introduced by a later event is absent when querying an earlier sequence, rejecting a non-numeric `asOfSequence` (`400`), and rejecting reconstruction with a key from a different project (`403`). Same `afterEach` cleanup pattern, extended to also delete `event_reducers` rows. | End-to-end proof that the declarative reducer config in `src/event-reducers` and the fold logic in `src/aggregates/reduce-events.ts` actually agree when wired through real HTTP + a real database — the pure-function unit tests in `reduce-events.spec.ts` cover the fold logic in isolation, but only this suite proves the whole path (register rule → append event → reconstruct) works. |
| `snapshots-and-replay-jobs.e2e-spec.ts` | Boots the app and exercises Phase 6 end-to-end against real Postgres + Redis + BullMQ (no mocking): appending 21 events to cross the snapshot threshold and polling until the async `snapshot-creation` job produces a `Snapshot` row (`waitForSnapshot` helper), confirming `GET .../state` both uses that snapshot for the latest state and correctly ignores it for a query *before* the snapshot's sequence number; creating a `POST /v1/projects/:id/replay-jobs` scoped to an `aggregateType` and polling until `completed` (`waitForJobCompletion` helper), asserting its `result` summary; running a replay job **twice** with no new events in between and asserting the second run is a safe no-op (`snapshotsCreated: 0`, no failures) rather than crashing on a duplicate-snapshot unique-constraint error; and project isolation on both replay-job endpoints (`403` with a key from a different project). | The "run twice" test is the regression test for a real bug found via manual testing, not code review: an early `SnapshotsService.createSnapshot` always attempted to `create` a new snapshot row, which correctly worked the first time but crashed with `Unique constraint failed on uq_snapshot_aggregate_sequence` the second time nothing had changed — the replay-job processor caught it as a per-aggregate failure (didn't crash the whole job) but it should never have been treated as a failure at all. See `src/snapshots/README.md` for the fix (a pre-check plus a caught `P2002` as a fallback for the concurrent-race case). The polling helpers exist because snapshot creation and replay-job execution are both genuinely asynchronous (BullMQ workers) — the HTTP response returns before the work is done, so tests must poll rather than assert immediately. |
| `jest-e2e.json` | Jest config for e2e specs: `rootDir` one level up (repo root), matches `*.e2e-spec.ts`, transforms via `ts-jest`, and maps `./x.js` → `./x` (`moduleNameMapper`) so the generated Prisma client's `.js`-suffixed internal imports resolve against the `.ts` sources under `ts-jest`. Run via `npm run test:e2e`. | Kept separate from the unit-test Jest config in `package.json` since e2e specs need a different `rootDir`/test match pattern and take longer to run (real app bootstrap, real DB connections). The `moduleNameMapper` entry exists because Prisma 7's generated client is written as `nodenext`-style TS (importing its own siblings with explicit `.js` extensions), which `ts-jest` can't resolve without it — this only ever surfaced once a spec first pulled in `PrismaService` transitively. |

`npm run test:e2e` runs via `node --experimental-vm-modules node_modules/jest/bin/jest.js ...` (see `package.json`) rather than plain `jest` — Prisma 7's WASM query-compiler loader uses dynamic `import()`, which Jest's CommonJS transform can't execute without that Node flag.

Since `snapshots-and-replay-jobs.e2e-spec.ts` was added, a "worker process has failed to exit gracefully" warning sometimes appears after a full parallel run — this is Jest's default multi-worker teardown racing with BullMQ's async Redis (`ioredis`) disconnect, not a real leak: it does not reproduce under `npm run test:e2e -- --detectOpenHandles` (serial), and every test still passes either way. Investigate further only if it starts actually failing a run.
