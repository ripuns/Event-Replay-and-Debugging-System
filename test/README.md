# test

End-to-end (e2e) tests — boot the full Nest app (`AppModule`) and hit real HTTP routes via `supertest`, as opposed to the isolated unit specs colocated with their modules (e.g. `src/modules/health/health.controller.spec.ts`).

## Files

| File | Purpose | Why |
|---|---|---|
| `health.e2e-spec.ts` | Boots the app with the global `/v1` prefix and asserts `GET /v1/health` returns `{ status: 'ok', service: 'replaydb-api', timestamp }`. | Confirms the app actually starts end-to-end (config validation, module wiring, DI graph) — not just that individual units work in isolation. |
| `organization.e2e-spec.ts` | Boots the app and hits real `/v1/organizations` routes against the live Postgres from `.env`'s `DATABASE_URL`: creating an org with a bootstrapped `firstProject`+API key, creating a bare org (no `firstProject`), and confirming `GET /v1/organizations/:id` is rejected without a valid key. Cleans up every org (and cascaded projects/keys) it creates in `afterEach` via `PrismaService`. | Verifies the atomic org+project+key bootstrap transaction actually persists correctly and that the `ApiKeyGuard`/org-id check on `GET /v1/organizations/:id` works against a real database, not just in isolation. |
| `projects.e2e-spec.ts` | Boots the app and exercises `/v1/organizations/:orgId/projects`, `/v1/projects/:id`, and `/v1/projects/:id/api-keys`: creating a second project in an org with an existing key, confirming a key from one project is rejected (`403`) on another project in the same org, confirming a key from a different org is rejected (`403`) on `:orgId/projects`, confirming no key is rejected (`401`), and minting an additional key for a project. Same `afterEach` cleanup pattern as `organization.e2e-spec.ts`. | This is the actual proof of the project-isolation guarantee described in `src/common/auth/README.md` and `database/migrations/README.md` — a passing suite here means the composite-FK isolation at the DB level and the guard-level isolation at the HTTP level agree with each other. |
| `events.e2e-spec.ts` | Boots the app and exercises `POST /v1/projects/:id/events`: auto-creating an aggregate on its first event (sequence number `1`), independent/increasing sequence numbers across separate `append` calls to the same vs. different aggregates, **15 concurrent appends to a brand-new aggregate** asserted to produce unique gapless sequence numbers `1..15` with no `500`s, and rejection (`401`) without a valid key. Same `afterEach` cleanup pattern (deletes events/aggregates/keys/projects/orgs it created). | The concurrency test is not a hypothetical — it's the regression test for a real race condition found during manual load testing (`EventsRepository.findOrCreateAggregateForUpdate`'s original `Prisma.upsert()`-based implementation crashed under concurrent first-appends to a new aggregate; see `src/events/README.md` for the root cause and fix). Keeping this test running against the real Postgres, not a mock, is what actually catches this class of bug — a mocked Prisma client can't reproduce a `READ COMMITTED` race. |
| `aggregates.e2e-spec.ts` | Boots the app and exercises `GET /v1/projects/:id/aggregates/:aggregateId/state`: registering `set`/`merge`/`append` reducer rules, appending a mix of mapped and unmapped event types and confirming the final reconstructed state matches exactly (including that the unmapped event contributed nothing), point-in-time reconstruction via `?asOfSequence=N` confirming a field introduced by a later event is absent when querying an earlier sequence, rejecting a non-numeric `asOfSequence` (`400`), and rejecting reconstruction with a key from a different project (`403`). Same `afterEach` cleanup pattern, extended to also delete `event_reducers` rows. | End-to-end proof that the declarative reducer config in `src/event-reducers` and the fold logic in `src/aggregates/reduce-events.ts` actually agree when wired through real HTTP + a real database — the pure-function unit tests in `reduce-events.spec.ts` cover the fold logic in isolation, but only this suite proves the whole path (register rule → append event → reconstruct) works. |
| `snapshots-and-replay-jobs.e2e-spec.ts` | Boots the app and exercises Phase 6 end-to-end against real Postgres + Redis + BullMQ (no mocking): appending 21 events to cross the snapshot threshold and polling until the async `snapshot-creation` job produces a `Snapshot` row (`waitForSnapshot` helper), confirming `GET .../state` both uses that snapshot for the latest state and correctly ignores it for a query *before* the snapshot's sequence number; creating a `POST /v1/projects/:id/replay-jobs` scoped to an `aggregateType` and polling until `completed` (`waitForJobCompletion` helper), asserting its `result` summary; running a replay job **twice** with no new events in between and asserting the second run is a safe no-op (`snapshotsCreated: 0`, no failures) rather than crashing on a duplicate-snapshot unique-constraint error; and project isolation on both replay-job endpoints (`403` with a key from a different project). | The "run twice" test is the regression test for a real bug found via manual testing, not code review: an early `SnapshotsService.createSnapshot` always attempted to `create` a new snapshot row, which correctly worked the first time but crashed with `Unique constraint failed on uq_snapshot_aggregate_sequence` the second time nothing had changed — the replay-job processor caught it as a per-aggregate failure (didn't crash the whole job) but it should never have been treated as a failure at all. See `src/snapshots/README.md` for the fix (a pre-check plus a caught `P2002` as a fallback for the concurrent-race case). The polling helpers exist because snapshot creation and replay-job execution are both genuinely asynchronous (BullMQ workers) — the HTTP response returns before the work is done, so tests must poll rather than assert immediately. The snapshot-sequence assertion in this file's first test was loosened from an exact `'20'` to `>= 20` once Phase 7's caching work changed timing enough to expose that the exact value was never actually guaranteed — see `src/aggregates/README.md`'s "A real bug found via testing" note. |
| `cache.e2e-spec.ts` | Boots the app and exercises Phase 7's Redis caching end-to-end against a real `ioredis` client (not a mock): confirms `GET .../state` populates `aggregate-state:{id}:latest` in Redis on a miss and returns the identical value on a subsequent hit; confirms a new `POST .../events` append deletes that `:latest` key immediately (`expect(await redis.get(key)).toBeNull()`) and the very next read reflects the new event rather than any stale cached value; confirms a historical `?asOfSequence=N` entry is cached under its own `:seq:{N}` key and **survives** a later append that invalidates `:latest` — proving the two are invalidated independently, exactly as `src/cache/README.md` documents. | This is the actual proof that the invalidation design (only `:latest` keys are ever deleted; `:seq:{N}` keys live forever) behaves as intended against a real Redis instance, not just in the design doc — a mocked cache client couldn't catch a bug where, say, invalidation accidentally deleted the wrong key pattern. |
| `auth-edge-cases.e2e-spec.ts` (Phase 8) | Boots the app and covers API-key auth paths not exercised elsewhere: a revoked key (`prisma.apiKey.update({ data: { revokedAt: new Date() } })`) rejected with `401`; an expired key (`expiresAt` in the past) rejected with `401`; a key with a *future* `expiresAt` still accepted; malformed `Authorization` headers (no `Bearer` prefix, empty token, wrong scheme) rejected with `401`; a well-formed but nonexistent key rejected with `401`. | There is no revoke/expire endpoint anywhere in the app (confirmed by reading `src/api-keys/*` and grepping for `revokedAt`/`expiresAt` — the only place either field is ever set is directly via Prisma), so these are the only tests that can exercise `ApiKeyService.verify()`'s revocation/expiry branches at all — every other e2e spec only ever creates fresh, valid keys. |
| `validation-edge-cases.e2e-spec.ts` (Phase 8) | Boots the app and covers `class-validator` DTO rejection paths grouped by endpoint: events (missing required fields, non-integer/non-positive `eventVersion`, invalid `occurredAt`, unknown properties rejected by `forbidNonWhitelisted`), event-reducers (invalid `operation` enum value, `merge`/`append` missing `field` via the DTO's `@ValidateIf`, `set` correctly *not* requiring `field`), and organizations (missing `name`, over-length `name`, a malformed nested `firstProject` failing `@ValidateNested`). | Before this file, the only `400` assertion anywhere in the e2e suite was `aggregates.e2e-spec.ts`'s malformed-`asOfSequence` check — which is a manually-thrown `BadRequestException`, not a DTO validation failure. No test previously proved the DTOs' `class-validator` decorators actually reject anything end-to-end through the real `ValidationPipe`. Grouped into one file by "DTO rejection cases" rather than split per DTO, per the user's explicit preference to avoid a file-per-scenario explosion. |
| `health-readiness.e2e-spec.ts` (Phase 8) | Boots the app and confirms `GET /v1/health/ready` returns `200` with `{ status: 'ready', checks: [{ name: 'database', status: 'ok' }, { name: 'redis', status: 'ok' }] }` against the real docker-compose Postgres/Redis. | The not-ready/`503` path is deliberately **not** tested here — see the comment in the file itself: a synthetic e2e test (swapping in a second `ioredis` client pointed at an unreachable port via a DI `overrideProvider`) caused Jest to hang indefinitely on module teardown, and wasn't worth chasing further given the failure path is already covered by `src/modules/health/health.controller.spec.ts`'s mocked unit test plus manual verification against the real stack (documented in `src/modules/health/README.md`). |
| `jest-e2e.json` | Jest config for e2e specs: `rootDir` one level up (repo root), matches `*.e2e-spec.ts`, transforms via `ts-jest`, maps `./x.js` → `./x` (`moduleNameMapper`) so the generated Prisma client's `.js`-suffixed internal imports resolve against the `.ts` sources under `ts-jest`, and loads `jest.setup.ts` (Phase 8) before any spec runs. Run via `npm run test:e2e`. | Kept separate from the unit-test Jest config in `package.json` since e2e specs need a different `rootDir`/test match pattern and take longer to run (real app bootstrap, real DB connections). The `moduleNameMapper` entry exists because Prisma 7's generated client is written as `nodenext`-style TS (importing its own siblings with explicit `.js` extensions), which `ts-jest` can't resolve without it — this only ever surfaced once a spec first pulled in `PrismaService` transitively. |
| `jest.setup.ts` (Phase 8) | Sets `process.env.QUEUE_METRICS_POLL_INTERVAL_MS` to a very large value (1 hour) before any e2e spec runs. | Every e2e spec file boots its own full `AppModule`, which (since Phase 8 added `MetricsModule`) means `QueueMetricsService`'s Redis-polling loop also spins up fresh per spec file. This keeps that polling out of the way during the test run (production keeps its 10s default; only the test run is slowed to effectively off) — a reasonable precaution, though it turned out **not** to be the cause of the flaky replay-job failure described below; that turned out to be a separate, unrelated issue. |

`npm run test:e2e` runs via `node --experimental-vm-modules node_modules/jest/bin/jest.js ...` (see `package.json`) rather than plain `jest` — Prisma 7's WASM query-compiler loader uses dynamic `import()`, which Jest's CommonJS transform can't execute without that Node flag. It also passes `--runInBand` (Phase 8) to rule out cross-worker-process contention as a variable while investigating the known issue below — this did not fix it, but is harmless to keep (e2e tests hit real shared infra either way, so parallel workers were never a reliability win here).

Since `snapshots-and-replay-jobs.e2e-spec.ts` was added, a "worker process has failed to exit gracefully" warning sometimes appears after a full parallel run — this is Jest's default multi-worker teardown racing with BullMQ's async Redis (`ioredis`) disconnect, not a real leak: it does not reproduce under `npm run test:e2e -- --detectOpenHandles` (serial), and every test still passes either way. Investigate further only if it starts actually failing a run.

## Known issue: `snapshots-and-replay-jobs.e2e-spec.ts` can flake when the full suite runs together

The two replay-job tests in this file (`runs a replay job scoped to an aggregateType...` and `running a replay job twice...`) reliably pass when this one spec file is run alone, but can intermittently time out (`Replay job <id> did not finish within 10000ms`) when the *entire* e2e suite runs together — confirmed via `docker exec replaydb_redis redis-cli client list`, which shows more live `bzpopmin` (BullMQ worker) connections than the two real queues should ever need. The root cause: every e2e spec file boots its own complete `AppModule` (including its own `SnapshotCreationProcessor`/`ReplayJobProcessor` BullMQ workers) in `beforeEach`, and `app.close()` in `afterEach` does not always fully close the underlying BullMQ worker connections before the next spec file's app boots its own. A leftover worker from an earlier, already-finished spec file's app instance can then win the race to pick up a job created by a *later* spec file, and crash (`Cannot read properties of undefined (reading 'Socket')`) because the DI graph it belongs to (Prisma client, etc.) was already torn down — the job is marked failed/never completes, and the waiting test times out.

This is a **test-infrastructure gap, not a product bug**: in a real deployment there is exactly one running app instance, so this "stale worker from a previous instance" scenario cannot occur. Every actual Phase 8 feature (readiness checks, metrics, tracing) and every core snapshot/replay-job feature was independently verified working correctly via direct manual testing against a live stack (see `src/observability/README.md` and `src/snapshots/README.md`).

Attempted fix: explicitly calling `queue.close()` on both BullMQ queues in `afterEach` before `app.close()` (closing the queue is documented to cascade into closing its worker). This did **not** resolve it — the same stale connections persisted afterward, meaning the leak is deeper than what's reachable from a single spec file (likely in how `@nestjs/bullmq`'s connection/module instance sharing behaves across many separately-compiled `TestingModule`s against the same Redis). Properly fixing this would mean either sharing one `AppModule` instance across all e2e spec files, or a more invasive rewrite of how BullMQ connections are scoped in tests — both bigger structural changes than justified by one intermittently-flaky test. If this starts failing consistently (not just intermittently) or spreads to other tests, revisit then.
